## Decisions

### AD-001
- **Decision**: Across this entire project, the agent never authors production or test implementation code. The user implements every task; the agent operates in mentor mode (Level 2-3 by default: explains concepts, points at the approach, gives isolated pseudocode/examples on request) and reviews the user's code before the task is marked done. The agent still runs the gate (tests) and creates the atomic commit once the user's code passes.
- **Reason**: `.specs/RFC.md` states the explicit purpose of this project is for the user to learn Kafka, Flink, architecture design, and observability tooling hands-on, using `.claude/skills/technical-learning-mentor` to force their own reasoning. It explicitly says the agent must not develop the code in their place.
- **Trade-off**: Slower delivery cadence than standard tlc-spec-driven execution. Agent-made commits carry a `Co-Authored-By: Claude` trailer per this harness's convention, which the user accepted knowingly (git history will show it).
- **Scope**: Governs the Execute phase for every feature under `.specs/features/` in this repository, superseding the skill's default "agent implements each task" behavior. **Amended by AD-002** for the unit-test-authoring exception, **amended by AD-003** (agent no longer creates the commit either - the "creates the atomic commit" clause above is superseded), **amended by AD-007** (the authorship boundary extends to structural decisions in a paired planning skill's Design-phase artifacts, not just Execute - enforced at the `technical-learning-mentor` skill level so it travels with the skill across projects, not recorded as project-local logic here).
- **Date**: 2026-08-05
- **Status**: active

### AD-002
- **Decision**: The agent may author unit test code directly (Level 5), but only when the class/module under test is already functional - its production implementation is complete and working, and only test coverage is missing or broken - **and** the user clearly and explicitly asks for it in-session. It does not extend to production code under any circumstance, and does not apply while the class itself is still mid-implementation as part of an in-progress task (mentor mode still governs that case even on explicit request). The same explicit-ask gate also covers small refactorings of already-working code (the kind CLAUDE.md's "small, explicitly-requested and user-confirmed fixes" clause already allowed outside the formal flow) - inside `tlc-spec-driven` Execute too, not only outside it.
- **Reason**: User request - writing exhaustive unit tests for code that already works and was already designed/reasoned through by the user has lower learning value than the design/implementation work itself. Originally this exception was gated behind the `/mentor-help` slash command; that command was removed from `.claude/commands/`, so the gate is now the user's explicit in-session request instead of a specific command's invocation - same substantive conditions, different trigger.
- **Trade-off**: Narrows AD-001's blanket "never authors test code" rule. The boundary condition ("is the class already functional?", "did the user clearly ask?") requires judgment call each time - if ambiguous, the agent should ask rather than assume the exception applies.
- **Scope**: Amends AD-001. Governs any explicit user request for test authoring or small refactoring of already-functional code, inside or outside the `tlc-spec-driven` formal flow; does not change default mentor-mode behavior for unassisted requests or for code that is still mid-implementation.
- **Date**: 2026-08-07 (amended 2026-08-17: `/mentor-help` trigger replaced with explicit-request trigger after the command's removal; scope extended to small refactorings)
- **Status**: active

### AD-003

The user makes every commit. The agent may stage changes, run gates, and propose a commit message, but stops short of committing.

- **Scope**: Project-wide, all workflows, supersedes the "creates the commit" clause in `AD-001` and any similar clause in `.claude/skills/tlc-spec-driven` (that skill's default "the orchestrator creates the commit" behavior does not apply here). Also recorded in `CLAUDE.md`'s Critical interaction rule.

### AD-004
- **Decision**: Every component that adapts an external, source-specific data shape into the pipeline's internal common shape (ingestion clients/engines today, the Flink normalization job going forward) is built behind a pluggable port/ABC with one concrete implementation per source - never with a source's shape baked into shared pipeline code. The internal common event envelope stays domain-neutral (event id, event type, actor, observed timestamp, schema version, a generic `partition_key`) and never encodes VCS-specific vocabulary (`repo_name`, `org_login`, etc.) as top-level fields; those live in a source-specific fields block populated by that source's normalizer/engine.
- **Reason**: The user's long-term intent for this project is to grow it into an API-agnostic real-time ingestion/analytics platform - register arbitrary APIs (not just GitHub/GitLab; e.g. weather or financial/monetary APIs) and stream + aggregate their events, to stress-test the pipeline's generality. GitHub/GitLab are the first two sources, not the permanent shape of the domain. `ingestion/ports.py`'s `IngestionClientBase`/`IngestionEngineBase`/`IngestionPublisherBase` already follow this discipline (GitHub concrete, GitLab stubbed); this decision extends the same discipline to the Flink normalization layer and any future consumer, without building out non-GitHub sources now.
- **Trade-off**: A small, constant overhead (interface boilerplate for a single concrete implementation) paid on every new pipeline stage, in exchange for the next new source - or the eventual platform generalization - being an additive change instead of a rewrite. Does not mean the platform gets built now - RFC's incremental-MVP philosophy still governs; only GitHub is implemented per source today.
- **Scope**: Applies to any future component that translates a source-specific payload into the pipeline's internal representation. The `flink-normalization` feature's normalizer is the first consumer of this decision. Existing `ingestion/` code already complies retroactively; no refactor required there. **Amended by AD-006** (2026-08-17): the "one concrete implementation per source" *mechanism* is superseded for the normalization layer - a contract-driven design has one implementation for all sources, with the contract varying instead of the class. The *principle* (no source-specific vocabulary in shared pipeline code, domain-neutral envelope) is unchanged and better served, since no source-specific code exists at all. The port/ABC is retained as the escape hatch for a source too irregular for a declarative contract.
- **Date**: 2026-08-10
- **Status**: active (mechanism amended by AD-006)

### AD-005
- **Decision**: `docker/` is renamed to `infra/docker/` (the pre-existing empty `infra/` scaffold becomes the umbrella for provisioning tooling). Kubernetes and Terraform remain opportunistic per the RFC, but two concrete triggers were identified rather than leaving them abstract: (1) Kubernetes becomes worth adopting once the local stack (Kafka + Flink + OpenSearch + Grafana) grows large/interdependent enough that Compose's orchestration (dependency ordering, scaling Flink task managers, health checks) starts to strain - a natural point given Flink normalization is landing now and OpenSearch/Grafana are next; if adopted, it lands as `infra/k8s/`. (2) Terraform becomes worth adopting only if the project starts provisioning real AWS resources (the user's free-tier account) - e.g. the EC2 instance/network hosting the K8s cluster - since Terraform provisions cloud-provider state that Compose/K8s manifests don't address; if adopted, it lands as `infra/terraform/`, scoped to that provisioning shell (network/compute), not to re-declaring Kafka/Flink as managed services. Terraform is not adopted before an AWS deployment decision is actually made. Separately, `ingestion/`, `flink/`, and `shared/` stay as top-level root folders rather than being nested under a `src/`: each is a distinct deployable service/stage of the pipeline (ingest, process, shared code) with its own lifecycle and Dockerfile, not interchangeable parts of one generic package - the repo root already communicates the pipeline's architecture (ingest → process, plus shared and infra) at a glance, which a `src/` wrapper would flatten without adding real benefit for an application (not a published library) at this scale. If the number of top-level service folders keeps growing, the fix on the table is grouping under `apps/`/`services/` (naming that's honest about "each subfolder is a deployable service"), not `src/`.
- **Reason**: User discussion on repo layout direction, weighing `docker/`→`infra/` and `ingestion/`/`shared/`/`flink/`→`src/` against the project's monorepo-of-services shape and the RFC's opportunistic K8s/Terraform goals; user then confirmed AWS free-tier usage is under consideration, which supplies the concrete Terraform trigger.
- **Trade-off**: One extra path segment for the Compose file and any tooling/docs referencing it (`docker/docker-compose.yml` → `infra/docker/docker-compose.yml`), in exchange for `infra/` being ready to hold `k8s/`/`terraform/` alongside it without another rename later. Declining `src/` means the root folder count grows by one per future genuinely-new deployable service, accepted as the honest reflection of a services monorepo rather than deferred to an artificial grouping.
- **Scope**: Project-wide layout. The `flink-normalization` feature is the first to reference the new `infra/docker/` path (topic provisioning, ingestion-as-compose-service, Flink cluster via compose - P1 story). K8s/Terraform adoption itself is not scheduled by this decision - only the trigger conditions and target paths are recorded, so a future decision to actually adopt either can point back here instead of re-litigating placement.
- **Date**: 2026-08-10
- **Status**: active

### AD-006
- **Decision**: Users register sources and declare normalization/transformation/aggregation by filling in a **contract expressed as data, never as Python**. Developers grow the Python codebase to add platform capabilities (new engines, new transform primitives, new sinks); adding a new *source* must never require a Python deploy, while adding a new *transform primitive* may. The contract is layered so the execution engine never surfaces to the user: a plain dotted path covers the common case, a small fixed set of named transforms covers the next tier, and a single documented key accepts a raw expression as the escape hatch. Storage starts as YAML files in the repo validated by a Pydantic model; the contract *format* is the API, so a future database + UI is a change of storage, not of format. Explicitly **not** planned: a hierarchy of Python configuration classes for the user to instantiate - declarative is the goal, a class-per-concept object model is not the route. Full reasoning, the three-layer model, the per-stage analysis, and the deferred items live in `.specs/PLATFORM.md`.
- **Reason**: The user's long-term intent (already recorded as `AD-004`) is an API-agnostic ingestion/analytics platform. `AD-004` fixed the *architectural* principle (pluggable ports per source); this decision fixes the *authoring* principle - who writes what, in which medium. The user has direct professional experience with an extraction platform whose abstractions are all expressed in Python, which works well but restricts authoring to people who write Python; they deliberately chose the other path here to learn it. `refactor/yaml-driven-source-config` (PR #5) already proved the approach for the source/endpoint stage.
- **Trade-off**: The platform must build and maintain a contract parser, validator, and interpreter that a Python-hosted configuration model would get for free from the language. Expressiveness is bounded by design, so some cases will need a developer to add a named transform rather than a user solving it alone. In exchange, source registration stops being a code change, and the contract format stays portable across storage backends and authoring surfaces (file, database, UI). Accepted limit of the current increment: YAML-in-git is not yet self-service for a non-technical user - it fixes the expensive part (the format) and defers the additive part (the UI).
- **Scope**: Project-wide, all pipeline stages. Supersedes nothing; `AD-004` stays active and complementary (it governs component structure, this governs authoring medium). **Inverts one feature-local choice**: `flink-normalization/design.md`'s "DataStream API, not Table API/SQL" was justified by normalization being arbitrary Python branching logic - under a contract-driven design that rationale no longer holds as a blanket rule, and the resolution is hybrid per stage (normalization → DataStream, aggregation → Flink SQL). The `flink-normalization` feature implements the first slice (normalization contracts only); transformation and aggregation contracts are deferred per `.specs/RFC.md`'s incremental-MVP approach.
- **Date**: 2026-08-17
- **Status**: active

### AD-007
- **Decision**: The `technical-learning-mentor` skill's authorship principle (the agent never writes the user's production code) now also covers structural/architectural decisions made inside a paired planning skill's own Design-phase artifacts (e.g. `tlc-spec-driven`'s `design.md`) - a class name, its file location, its method breakdown - not just source files. Before such a decision (one that passes the skill's `decide`-bucket test) is written into a design artifact, the user's own proposal is elicited first; the artifact is written to reflect what was reasoned through, not handed down. Purely mechanical Design decisions (library choice, config shape, already-conventioned layout) are unaffected. **The mechanism itself is not recorded here** - it lives in `.claude/skills/technical-learning-mentor/SKILL.md` (Core rule 1, "Session behaviour outside the commands") and `references/code-policy.md` ("Paired planning skills" section), because the skill is owned by the user and reused across projects; duplicating the rule text in this project-local file would leave every other project the skill is used in exposed to the same gap.
- **Reason**: User feedback, 2026-08-17. `streaming-ingestion`/P2 skipped the Design phase entirely (`spec.md`: "Design: none"), so `tasks.md` left class/file/method choices open for Execute - where mentor mode already governs, and the user got to reason through them (e.g. `RetryTimer`, `BoundedUniqueTracker` only named in retrospect). `flink-normalization` went through a full Design phase; the agent designed `FieldRule`/`NormalizationContract`/`ContractNormalizer`'s shape unilaterally there (Design/Tasks phases sit outside `AD-001`'s stated Execute-only scope), and `tasks.md` then transcribed those decisions as prescriptions - by the time Execute (mentor mode) started, the structural reasoning opportunity was already gone. `K-11` (`.mentor/features/flink-normalization/knowledge.md`) is the existing counter-example: it became a real `decide` objective precisely because `design.md`/`tasks.md` had *not* pre-decided it when the user asked. The first draft of this decision proposed recording the fix only in this file; the user pointed out that would not help a future project pairing spec-driven planning with this same skill, since `STATE.md` is per-repository and the skill is not.
- **Trade-off**: Design moves slower on components that carry a genuine structural decision (one more elicitation round before that part of `design.md` gets written) - unaffected for mechanical Design decisions, same pace as before. In exchange, the user keeps exercising "which class, where, what methods" at the moment the decision is genuinely open, in any project this skill is used in, not just this one.
- **Scope**: Amends `AD-001` (extends its authorship boundary from Execute-only to also cover a paired planning skill's Design phase); the enforceable mechanism lives in the skill, not in this repository. Applies to every feature under `.specs/features/` going forward. Retroactively applied to `flink-normalization`'s remaining structural tasks (T10 - Contract loader, T11 - `ContractNormalizer`) per the user's explicit confirmation; not reopened for T1-T9 (already shipped) or for `flink-normalization`'s already-written `design.md`/`tasks.md` (those stay as the record of what was decided, even though the process that produced them predates this decision).
- **Date**: 2026-08-17
- **Status**: active
