### AD-002
- **Decision**: The agent may author unit test code directly (Level 5), but only when the class/module under test is already functional - its production implementation is complete and working, and only test coverage is missing or broken - **and** the user clearly and explicitly asks for it in-session. ### AD-004
- **Decision**: Every component that adapts an external, source-specific data shape into the pipeline's internal common shape (ingestion clients/engines today, the Flink normalization job going forward) is built behind a pluggable port/ABC with one concrete implementation per source - never with a source's shape baked into shared pipeline code. The internal common event envelope stays domain-neutral (event id, event type, actor, observed timestamp, schema version, a generic `partition_key`) and never encodes VCS-specific vocabulary (`repo_name`, `org_login`, etc.) as top-level fields; those live in a source-specific fields block populated by that source's normalizer/engine.
- **Scope**: Applies to any future component that translates a source-specific payload into the pipeline's internal representation. The `flink-normalization` feature's normalizer is the first consumer of this decision. Existing `ingestion/` code already complies retroactively; no refactor required there. **Amended by AD-006** (2026-08-17): the "one concrete implementation per source" *mechanism* is superseded for the normalization layer - a contract-driven design has one implementation for all sources, with the contract varying instead of the class. The *principle* (no source-specific vocabulary in shared pipeline code, domain-neutral envelope) is unchanged and better served, since no source-specific code exists at all. The port/ABC is retained as the escape hatch for a source too irregular for a declarative contract.
- **Date**: 2026-08-10
- **Status**: active (mechanism amended by AD-006)
- **Rationale**: [STATE-history.md#ad-004](STATE-history.md#ad-004)

### AD-005
- **Decision**: `docker/` is renamed to `infra/docker/` (the pre-existing empty `infra/` scaffold becomes the umbrella for provisioning tooling). Kubernetes and Terraform remain opportunistic per the RFC, but two concrete triggers were identified rather than leaving them abstract: (1) Kubernetes becomes worth adopting once the local stack (Kafka + Flink + OpenSearch + Grafana) grows large/interdependent enough that Compose's orchestration (dependency ordering, scaling Flink task managers, health checks) starts to strain - a natural point given Flink normalization is landing now and OpenSearch/Grafana are next; if adopted, it lands as `infra/k8s/`. (2) Terraform becomes worth adopting only if the project starts provisioning real AWS resources (the user's free-tier account) - e.g. the EC2 instance/network hosting the K8s cluster - since Terraform provisions cloud-provider state that Compose/K8s manifests don't address; if adopted, it lands as `infra/terraform/`, scoped to that provisioning shell (network/compute), not to re-declaring Kafka/Flink as managed services. Terraform is not adopted before an AWS deployment decision is actually made. Separately, `ingestion/`, `flink/`, and `shared/` stay as top-level root folders rather than being nested under a `src/`: each is a distinct deployable service/stage of the pipeline (ingest, process, shared code) with its own lifecycle and Dockerfile, not interchangeable parts of one generic package - the repo root already communicates the pipeline's architecture (ingest → process, plus shared and infra) at a glance, which a `src/` wrapper would flatten without adding real benefit for an application (not a published library) at this scale. If the number of top-level service folders keeps growing, the fix on the table is grouping under `apps/`/`services/` (naming that's honest about "each subfolder is a deployable service"), not `src/`.
- **Scope**: Project-wide layout. The `flink-normalization` feature is the first to reference the new `infra/docker/` path (topic provisioning, ingestion-as-compose-service, Flink cluster via compose - P1 story). K8s/Terraform adoption itself is not scheduled by this decision - only the trigger conditions and target paths are recorded, so a future decision to actually adopt either can point back here instead of re-litigating placement. **Amended by RFC.md** (2026-08-28): Kubernetes moved from opportunistic to a required learning goal in `.specs/RFC.md`. The trigger condition named here - "5 ingestion processes" as part of what would make Compose's orchestration strain - was already implicit in the project's one-process-per-source model (`ingestion`'s single compose service today reflects one wired source, not an architecture that assumes one); `.specs/RFC-conviction-index.md` gives that trigger a concrete path (5 sources, 2 transport models). Terraform's trigger condition is unaffected and stays opportunistic.
- **Date**: 2026-08-10
- **Status**: active (Kubernetes opportunism amended, see above)
- **Rationale**: [STATE-history.md#ad-005](STATE-history.md#ad-005)

### AD-006
- **Decision**: Users register sources and declare normalization/transformation/aggregation by filling in a **contract expressed as data, never as Python**. Developers grow the Python codebase to add platform capabilities (new engines, new transform primitives, new sinks); adding a new *source* must never require a Python deploy, while adding a new *transform primitive* may. The contract is layered so the execution engine never surfaces to the user: a plain dotted path covers the common case, a small fixed set of named transforms covers the next tier, and a single documented key accepts a raw expression as the escape hatch. Storage starts as YAML files in the repo validated by a Pydantic model; the contract *format* is the API, so a future database + UI is a change of storage, not of format. Explicitly **not** planned: a hierarchy of Python configuration classes for the user to instantiate - declarative is the goal, a class-per-concept object model is not the route. Full reasoning, the three-layer model, the per-stage analysis, and the deferred items live in `.specs/PLATFORM.md`.
- **Scope**: Project-wide, all pipeline stages. Supersedes nothing; `AD-004` stays active and complementary (it governs component structure, this governs authoring medium). **Inverts one feature-local choice**: `flink-normalization/design.md`'s "DataStream API, not Table API/SQL" was justified by normalization being arbitrary Python branching logic - under a contract-driven design that rationale no longer holds as a blanket rule, and the resolution is hybrid per stage (normalization → DataStream, aggregation → Flink SQL). The `flink-normalization` feature implements the first slice (normalization contracts only); transformation and aggregation contracts are deferred per `.specs/RFC.md`'s incremental-MVP approach.
- **Date**: 2026-08-17
- **Status**: active
- **Rationale**: [STATE-history.md#ad-006](STATE-history.md#ad-006)

### AD-008
- **Decision**: Authorship is decided **per task**, in advance, from the knowledge state - not as a blanket rule. Every task in a feature carries one of three levels, assigned at `/mentor-map` and recorded in `.mentor/features/<slug>/map.md`: `own` (the user authors production code and tests), `paired` (the user makes and defends the decision the task carries, logged as evidence; the agent then writes the mechanical body around it), `deliver` (the agent authors, the user reviews). The level is derived from each task's objectives in `.mentor/knowledge.md`: any objective below its `target`, carrying an open misconception, or due by `retention.md`'s dual clock -> `own`/`paired`; no objective, or all at/above target and not due -> `deliver`. Read `state` against `target`, never tag membership. The level is read from `map.md` at Execute, **never re-derived in the moment** - inferring it at request time is the agent deciding whether the agent may write the code. Promotion is free; demotion mid-feature requires a dated line in `map.md`'s notes. Code the agent authored under `deliver` never becomes evidence in `.mentor/`. A companion scope gate applies at task generation: every task must name the objective it advances or be explicitly marked `deliver`.
- **Scope**: Amends `AD-001` - its blanket "the agent never authors production code" now reads "never for `own` tasks, and never for the decision half of `paired` tasks". `AD-002` becomes mostly **derivable** rather than an enumerated exception (tests for already-working code and small refactors are `deliver` by the ordinary rule); it stays written down only for the case levels don't reach - an explicit ask on a task still at `own`/`paired` whose production code is already finished. `AD-003` (no agent commits) is untouched and remains absolute - it is orthogonal to authorship. `AD-007` is unchanged and now has a sibling at Execute: `paired` is the same elicit-first shape applied to tasks rather than Design artifacts. **The enforceable mechanism is not recorded here** - it lives in `.claude/skills/technical-learning-mentor` (`SKILL.md` core rule 8 and "Session behaviour outside the commands", `references/code-policy.md`'s "Task authorship levels", `commands/mentor-map.md` step 4b and "Remapping"), for the same reason `AD-007` gave: the skill is the user's and is reused across projects, while `STATE.md` is per-repository. `.claude/rules/interaction-protocol.md` carries the project-local backstop. `tlc-spec-driven` was deliberately left unmodified - it has no repository of its own and would lose any change on reinstall. Applied retroactively to `flink-normalization`'s open tasks (T11-T22, classified in `map.md` on 2026-08-18); closed tasks T1-T10 are not reclassified.
- **Date**: 2026-08-18
- **Status**: active
- **Rationale**: [STATE-history.md#ad-008](STATE-history.md#ad-008)

### AD-009
- **Decision**: The aggregation stage has no YAML contract. The platform's user is now assumed capable of authoring SQL directly, not only YAML - so the Flink SQL query itself (a `.sql` file, not Python, not YAML) *is* the declarative contract for this stage. It still satisfies `AD-006` (a contract is data the platform interprets, never Python the user edits) without a friendly-vocabulary layer on top, because the engine here is already a lingua franca the target user is assumed to know.
- **Scope**: Amends `AD-006`/`PLATFORM.md`'s "Aggregation should compile to Flink SQL" section and its "What is deliberately deferred" list - "transformation and aggregation contracts" no longer applies to aggregation; there is no aggregation contract to design later, by design. Normalization is unaffected (JMESPath stays obscure enough to justify the friendly tier); transformation stays open/TBD. `PLATFORM.md`'s "Tiers of expressiveness" section gains a note: the tier discipline assumes an engine the user should not have to learn directly - when the engine is already a lingua franca (SQL), the raw-expression tier *is* the product, not an escape hatch. First applied by the `flink-aggregation` feature.
- **Date**: 2026-08-24
- **Status**: active
- **Rationale**: [STATE-history.md#ad-009](STATE-history.md#ad-009)
